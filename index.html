Workflow SDK · Clojure / Babashka

greenspecification · 2026-10-29

Coding agents write deployment code directly. Terraform and Ansible existed because hand-writing cloud automation was too slow and too fragile; an agent now writes the steps that call cloud CLIs and APIs itself. The colors are the foundation for that code: three workflow SDKs — green (Clojure), red (TypeScript) and blue (Python) — sharing one model.

green is the canonical colour. Build your own package on it, or start from PocketDeploy, the starter package built on blue. green has no OpenTofu or Ansible integration any more: OpenTofu and Ansible support was removed on 2026-10-29, and steps call the tools they need directly.

1. Philosophy

  • Data in, data out. All state crossing step boundaries is one immutable map, opts. A step reads it and returns a new one.
  • The graph is data, routing is a function. A static wire-fn declares the happy path; an optional next-fn decides at run time where each branch goes.
  • Unix-style outcomes. Success and failure travel in opts as an exit code, not as exceptions.
  • Cross-cutting behaviour is advice. Dry-run, progress, validation, retries and locks wrap steps without touching their code or the wiring.
  • Desired state is a file; secrets are not. A YAML file describes what should exist. Credentials arrive through COLORS_PAR_* environment variables.
  • Steps own side effects. A step calls a CLI (gcloud, doctl, oci, uname) or an HTTP API directly. green provides the engine, not the integrations.
  • Pure construction. Every constructor and advice function returns a new workflow value; workflows are safe to share and branch.

2. The opts contract

A workflow run threads a single map. Keys under :green/* are reserved for the engine; everything else uses the package's own namespace (:hello/kernel) or flat desired-state keys (:name, :do-token).

3. Steps and errors

A step is a function opts -> opts, named in the graph by a qualified keyword.

(defn uname-step [opts]
  (let [{:keys [exit out err]} (shell/sh "uname" "-s")]
    (if (zero? exit)
      (assoc opts :hello/kernel (str/trim out))
      (assoc opts :green/exit exit :green/err (str "uname failed: " err)))))
  • A step fails by returning :green/exit > 0. A branch stops after a failing step unless next-fn routes it.
  • A thrown exception is caught and converted to :green/exit 1 (or the :green/exit in its ex-data) with :green/err and :green/trace. A non-map return is also a failure.
  • A successful step may omit :green/exit; the engine normalises it to 0.
  • wf/failed? is the predicate for a positive exit, for steps composed of sub-steps.

4. Workflows: wire-fn and next-fn

(wf/workflow {:start   :hello/start   ; required
              :end     nil            ; optional slice boundary: runs, then stops
              :wire-fn wire-fn        ; required
              :next-fn nil})          ; optional

(wire-fn step run-opts) -> [step-fn & next-steps] is the static graph for a run. run-opts is the initial opts of the run, constant for its duration, so the graph may depend on stable inputs such as :green/event:

(defn wire-fn [step run-opts]
  (case [(:green/event run-opts) step]
    [:create :hello/start]  [start-step :hello/uname :hello/write]
    [:create :hello/uname]  [uname-step :hello/check]
    [:create :hello/write]  [write-step :hello/check]
    [:create :hello/check]  [check-step]
    [:delete :hello/start]  [start-step :hello/remove]
    [:delete :hello/remove] [remove-step]))

(next-fn step default-next opts) -> [[next-step opts] ...] is optional dynamic routing: fan out one branch per item, branch on a result, or route failures. default-next is the wire-fn's successor list. Without a next-fn, a failed branch stops and a successful one follows default-next with the same opts.

(defn next-fn [step default-next opts]
  (cond
    (wf/failed? opts) []
    (= step :app/start) (for [n (:nodes opts)] [:app/node (assoc opts :app/node n)])
    :else (map (fn [s] [s opts]) default-next)))

(wf/run workflow opts) runs from :start and returns the final opts; its :green/exit is the workflow's exit code.

5. Parallelism and joins

Several successors fork: each branch runs in its own future. The scheduler:

  1. keeps live branches and finished branches, grouping live ones by step;
  2. runs a step only when no other live branch can still reach it through the run's static wire-fn edges, so longer branches arrive before a join runs;
  3. runs ready work concurrently;
  4. on zero successors finishes a branch, on one continues, on several forks;
  5. runs a step reached by branches of different origins once, as a join, with the fork-point opts plus :green/branches (each branch's result);
  6. collapses a fork in which a branch failed: running siblings finish their current step, no further fork work starts, the join is skipped, and the result carries the worst exit plus all branch results;
  7. returns the single terminal result, or with several terminals the first failure, otherwise the last success.

A join step typically merges its branches: (apply merge opts (:green/branches opts)).

6. Composition

(wf/step sub-workflow {:in-fn f :out-fn g}) turns a whole workflow into an ordinary step: wire it, advise it, fan it out. :in-fn shapes the opts entering the sub-workflow; :out-fn (fn [opts sub-result] ...) merges the result back (default: the sub-result is the step's result). Its :green/exit propagates. A custom :in-fn should carry ambient keys such as :green/event and :green/dry-run if the sub-workflow needs them.

7. Advice

Emacs nadvice-style wrappers, attached by id. (wf/advice-add wf step how id f [props]) targets one step; (wf/advice-add-all wf how id f [props]) every step. advice-remove and advice-remove-all remove by id; re-adding an id replaces it.

  • Ordering. Per-step and all-steps advice stack in strict add order: the most recently added is outermost. {:depth n} (−100..100, default 0) overrides that: lower is further outside.
  • Scope. Registries are values inside the workflow, never process-global.
  • Inheritance. Through wf/step embeds, an enclosing run's advice applies to the embedded workflow's steps of the same name at any depth. At equal depth ancestor advice is outside child advice; an ancestor entry with the same id replaces the child's.
  • Inspection. (wf/advice-plan wf-or-chain step) returns the composed stack, outermost first, with :scope (:step/:all) and :level.

8. YAML desired state and COLORS_PAR_*

cli/read-state reads .yml/.yaml with yamlstar (YAML 1.2 core schema, pinned exactly so the red and blue ports read identical values) and anything else as EDN. Map keys become keywords at every depth. Under the core schema no, yes and on stay strings.

# green.yml — non-secret by rule
name: world
greeting-file: work/hello.txt

cli/read-pars overlays every COLORS_PAR_<UPPER_SNAKE> environment variable onto the matching flat key: COLORS_PAR_DO_TOKEN → :do-token. Values are coerced to the type of the value they replace (booleans and integers), and applying the overlay twice changes nothing. cli/par-name maps a key back to its variable name. The prefix is shared by all three colours.

Secrets never go in the desired-state file. Keys are kebab-case; credentials are supplied only as COLORS_PAR_* variables.

9. Dry-run, progress, lifecycle

green.dry-run

(dry-run/advise wf steps) attaches :around advice with id :green.dry-run/skip to each named step. With :green/dry-run set, the step prints dry-run: would run <step> (<event>) and returns exit 0 without running. Declare it last so it is outermost. Unadvised read-only steps still run.

green.progress

(progress/advise wf) adds all-steps :around advice (id :green.progress/progress) printing >>> step (event) on entry and <<< step (Nms) on exit. Output is synchronised across parallel branches.

green.lifecycle

(lifecycle/preflight opts {:defaults :overlay :validators :after-validate} [env]) merges defaults under opts, applies the overlay (typically cli/read-pars), then runs every validator (fn [opts env context]) in order, collecting the error strings it returns. Any error yields exit 2 with all errors joined; otherwise after-validate runs, or exit 0 is set. context carries :event and :real? (lifecycle/real-run?, false under dry-run).

10. CLI and the ./green launcher

./green <event> [-f|--file green.yml] [--start step] [--end step] [--dry-run]

(cli/run-cli workflow args config) parses arguments (unknown options are rejected), reads the desired-state file, stamps :green/state-file, overlays COLORS_PAR_*, stamps :green/event and :green/dry-run, applies --start/--end as a graph slice, and returns the final opts. Usage and file errors return exit 2. config accepts :default-file (default green.yml), :search-parents (find the nearest file upwards with cli/find-up) and :allowed-events. (cli/exec ...) does the same, prints :green/err/:green/trace to stderr and exits with :green/exit.

A package's ./green is a babashka script: it adds green as a git dependency pinned by :git/sha (or a working tree via GREEN_LIB_ROOT), defines its workflow, and calls cli/exec. green is not on Clojars.

((requiring-resolve 'babashka.deps/add-deps)
 {:deps {'io.github.getcolors/green
         {:git/url "https://github.com/getcolors/green.git"
          :git/sha "<commit>"}}})
(require '[green.cli :as cli] '[green.workflow :as wf])
;; ... steps, wire-fn, workflow ...
(cli/exec workflow *command-line-args*
          {:default-file "green.yml" :search-parents true
           :allowed-events [:create :delete]})

(cli/stage-dir opts tool [{:default-workdir :default-profile :state-file-key}]) resolves <state-file dir>/<:workdir or .colors>/<:profile>/<tool> for packages that render files; absolute workdirs are kept.

11. The example

examples/hello is a complete package in three files: the green launcher (holding the workflow), green.yml, and test/hello/launcher_test.clj. It is offline and harmless.

:hello/start (lifecycle preflight)
   ├─ :hello/uname   uname -s            (read-only, runs under --dry-run)
   └─ :hello/write   write greeting file
        ↘ ↙
   :hello/check      join: read the file back and verify
cd examples/hello
./green create --dry-run
./green create                         # hello, world (Linux)
COLORS_PAR_NAME=agent ./green create   # hello, agent (Linux)
./green delete

12. Testing

bb test                # Babashka
clojure -X:test        # JVM (cognitect test-runner)
clojure -T:build jar   # target/green-0.1.0.jar
bb docco               # regenerate docco.html

Steps are plain functions and cli/run-cli never exits, so packages test their workflows in-process with wf/run or run-cli, using :override advice to stub side effects. The example's test drives the real launcher as a subprocess (needs bb on PATH). CI runs both suites and builds the jar.
